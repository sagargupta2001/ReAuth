# Spec: Fluid Nested Sections

> Distilled from: builder review of the default login page, 2026-08-23
> Status: Implemented

---

## User Story

As a realm admin building a theme page, I want to nest blocks inside container
blocks and rearrange them at any depth, so that I can compose real layouts — a
centred row of text and a link, a two-column split, a grouped field set — instead
of a flat list of siblings.

---

## Actors

| Actor | Role in this feature |
|-------|---------------------|
| Realm Admin | Builds page structure in the Fluid builder: nests, reorders, and moves blocks. |
| End User | Sees the resulting layout on an auth page. No direct interaction. |
| Operator | Ships default blueprints that already use nesting (`theme_pages.rs`). |

---

## Context: what already works

This feature is **editing**, not modelling. The pieces already in place:

- `ThemeNode.children?: ThemeNode[]` exists and is persisted inside the page
  blueprint JSON.
- Both renderers already recurse: `FluidCanvas` and `FluidLoginScreen` render
  `node.children` for a `Box`, and `computeNodeVisuals` supplies the inner
  size classes so a nested box lays out correctly.
- The sections tree already *displays* children and slots recursively, and
  clicking a nested row selects it.
- The inspector already edits whichever node is selected, at any depth.
- `nodeUtils` already has recursive `findNodeById`, `updateNodeById`, and
  `removeNodeById`.
- The seeded login page already contains a nested `Box` (the
  "New on our platform? / Create an account" row).

What is missing is every **write** path that changes structure:

- Insert only appends to the page's root array: `onInsertNode(node, index)`.
- Reorder only permutes root siblings: `onReorderNodes(fromIndex, toIndex)`.
- There is no move-into, move-out-of, or reparent operation at all.

---

## Business Rules

1. A node may contain children only if its block declares that it accepts them.
   `Box` accepts children; `Text`, `Image`, `Icon`, `Divider`, `Link`, `Button`,
   and `ProviderButtons` do not.
2. Structural operations address nodes by **id**, not by index or path. Indices
   shift the moment a sibling moves, and a path captured before a mutation is
   stale after it.
3. A node cannot be moved into itself or into any of its own descendants. The
   tree must remain a tree.
4. Nesting is capped at a maximum depth. A drop that would exceed it is rejected
   with a reason, not silently ignored.
5. Slot children (`node.slots`) are part of a component's contract, not free
   composition. They are visible in the tree and selectable, but cannot be
   reordered, moved, or receive drops.
6. Children generated by `componentRegistry` expansion (an `Input`'s label, field
   container, and inner input) are render-time only. They never appear in the
   authored tree and are never drop targets.
7. Inserting from the block picker targets a specific parent and position, so
   "add inside this box" and "add after this row" are distinct actions.
8. Every structural change goes through `commitDraft`, so it lands in undo/redo
   and is persisted only by Save, like every other builder edit.
9. Reordering, nesting, and outdenting are reachable from the keyboard, not drag
   only.
10. An empty container renders a visible drop target in the tree, otherwise there
    is no way to put the first child into a new box.

**Edge cases:**

- Dropping a node onto its current position is a no-op, not an empty history entry.
- Removing a container removes its subtree (already true of `removeNodeById`).
- A container that becomes empty stays in the tree; it is not auto-pruned.
- Dragging the last child out of a container leaves an empty container, which
  must still show its drop target.
- A blueprint loaded from an older version, or hand-edited, may exceed the depth
  limit. It renders as-is; the limit constrains new operations only.
- A node dragged onto a non-container row is treated as a sibling drop
  (before/after), never as an attempt to nest.

## Domain Changes

### New Value Objects

```text
NodeDropIntent — where a dragged node should land relative to a target
  - Before: sibling immediately above the target
  - After:  sibling immediately below the target
  - Inside: last child of the target (containers only)

NodeLocation — an insertion address
  - parentId: string | null — null means the page's root list
  - index: number — position among that parent's children
```

### Modified Entities

```text
ThemeNode
  (no shape change — children already exists and already persists)
```

### New Block Capability

```text
FluidBlockDefinition
  + acceptsChildren: boolean — whether this block can contain other blocks
```

Declared per block in `model/blockCatalog.ts` so adding a future container type
(Grid, Stack, Columns) is a data change, matching how the inspector schema and
theme settings schema already work.

## Availability / Admin UX

- System/operator prerequisites: none
- Realm policy: none
- Flow composition: none
- Builder behavior:
  - A row's drop zones are top edge → *before*, bottom edge → *after*, middle →
    *inside* when the row accepts children. Non-containers expose only
    before/after.
  - The active zone is shown while dragging: a line between rows for
    before/after, a highlighted row for inside.
  - A rejected drop (cycle, depth limit, non-container) shows a
    not-allowed cursor and does not commit.
  - The block picker's "+" gains an inside-a-container affordance, so a new block
    can be added directly into a box.
  - Containers can be collapsed, so a deep tree stays navigable. Collapse state
    is view-only and not persisted to the draft.
  - Keyboard: `Tab` / `Shift+Tab` on a focused row indents into the previous
    sibling container / outdents to the parent's level; `Alt+Up` / `Alt+Down`
    reorder within the current parent.
- Simple mode UX: unchanged
- Advanced mode UX: unchanged

## Test Scenarios

1. **Happy path — nest into a container**
   - Given: a page with a `Text` node and an empty `Box`
   - When: the `Text` is dropped onto the middle of the `Box` row
   - Then: `Text` becomes a child of `Box`, the tree shows it indented one level
     deeper, and the canvas renders it inside the box

2. **Reorder within a container**
   - Given: a `Box` containing `Text` then `Link`
   - When: `Link` is dropped on the top edge of `Text`
   - Then: the box's children are `Link`, `Text`; no other node moves

3. **Move out of a container**
   - Given: a `Box` containing a single `Text`
   - When: `Text` is dropped on the bottom edge of a root-level sibling
   - Then: `Text` becomes a root sibling, and the `Box` remains present and empty
     with a visible drop target

4. **Validation failure — cycle**
   - Given: `Box A` containing `Box B`
   - When: `Box A` is dropped inside `Box B`
   - Then: the drop is rejected, the tree is unchanged, and no history entry is
     recorded

5. **Validation failure — non-container**
   - Given: a `Text` node and a `Link` node
   - When: `Link` is dropped on the middle of the `Text` row
   - Then: it is treated as a sibling drop, never as nesting

6. **Business rule edge case — depth limit**
   - Given: a chain of boxes already at `MAX_NESTING_DEPTH`
   - When: a node is dropped inside the deepest box
   - Then: the drop is rejected with a reason surfaced to the user

7. **Business rule edge case — slots are immutable**
   - Given: an `Input` with a `prefix` slot
   - When: the slot row is dragged, or a node is dropped on it
   - Then: nothing happens; slot rows are neither draggable nor drop targets

8. **Insert into a container**
   - Given: an empty `Box` is selected
   - When: a block is chosen from the picker's inside-container affordance
   - Then: the new node is appended to that box's children, not to the page root

9. **Undo**
   - Given: any completed structural change
   - When: undo is triggered
   - Then: the previous tree is restored exactly, including child order

10. **Keyboard parity**
    - Given: a focused root-level node preceded by a sibling `Box`
    - When: `Tab` is pressed
    - Then: the node becomes the last child of that `Box`, matching the drag result

11. **Renderer parity**
    - Given: a three-level nested tree
    - When: rendered by `FluidCanvas` and by `FluidLoginScreen`
    - Then: both produce the same structure and applied styles

12. **Error handling — stale drag**
    - Given: a drag started on a node that is removed before the drop
    - When: the drop fires
    - Then: the operation is discarded without throwing, and the tree is unchanged

## Out of Scope

- Dragging blocks directly on the canvas. The tree is the structural editor for
  this slice; canvas drag is a follow-up that should reuse the same
  `moveNode` / `resolveDrop` primitives.
- Multi-select and bulk move.
- Copy, paste, and duplicate of a subtree.
- Editing the children a `Component` generates internally (an `Input`'s label and
  field container). Those stay owned by `componentRegistry`.
- New container block types (Grid, Columns). The `acceptsChildren` flag makes them
  additive; this slice ships `Box` only.
- Absolute or overlay positioning, and auto-layout wrapping.
- Persisting collapse state across sessions.

## Resolved Questions

- [x] `MAX_NESTING_DEPTH` is **6** (`model/sectionTree.ts`), counted as levels
      with root nodes at level 1. It constrains new operations only; a deeper
      blueprint loaded from an older version still renders as authored.
- [x] Dropping onto a collapsed container **auto-expands** it, once per hover,
      so no drop lands out of sight.
- [x] Empty containers are **kept as authored**. Nothing prunes them, on Save or
      otherwise.
- [x] Collapse ships **in this slice**. Without it the tree is unreadable at the
      depth the drop zones now make reachable. State is view-only and lives in
      `FluidBlocksPanel`, never in the draft.
- [ ] Do the default blueprints in `theme_pages.rs` adopt nesting more widely now
      that this has shipped (for example wrapping the login fields in a field-set
      box), or stay flat? Deferred — no seed change was needed to ship the
      editing capability.

## Resolved: the keyboard binding

Rule 9 asked for indent and outdent on `Tab` / `Shift+Tab`. That shipped as a
compromise — consuming them only when a move was actually possible — because
binding them outright makes the panel a keyboard trap (WCAG 2.1.2). The
compromise still trapped focus anywhere in the middle of a tree, where a move
*is* always possible.

Replaced with `Alt+Right` (indent) and `Alt+Left` (outdent), alongside the
`Alt+Up` / `Alt+Down` reorder that rule 9 already had. One modifier, four
directions, and `Tab` is plain focus navigation again. This matters more since
canvas drag shipped: that is mouse-only, so the tree's keyboard path is the
accessible route to structural editing and cannot be a trap.

`FluidBlocksPanel.test.tsx` asserts `Tab` and `Shift+Tab` are never consumed.
